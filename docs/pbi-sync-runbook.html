02

Publishing a change

  1. Close Power BI Desktop. The first gate checks for it and will stop you.
  2. Commit your work. A publish has to map to a commit.
  3. Run the publish.
# from inside the project folder — the slug is inferred
sh ~/.claude/pbi-sync/bin/pbi-publish.sh

# or name it, from anywhere
sh ~/.claude/pbi-sync/bin/pbi-publish.sh sales-report

# see what would change without touching anything
sh ~/.claude/pbi-sync/bin/pbi-publish.sh sales-report --dry-run

Checking state at any time

sh ~/.claude/pbi-sync/bin/pbi-status.sh            # all projects
sh ~/.claude/pbi-sync/bin/pbi-status.sh sales-report    # one

Read-only. It reports unpublished commits, OneDrive drift, whether Desktop is open, and any held lock.

Flags you will rarely need

--init — first publish into a target, or one whose deliverable repo must be rebuilt. --force-overwrite — publish over drift, discarding whatever changed there. --min-ratio N — lower the file-count floor when a big deletion is genuinely intended.

03

When a gate stops you

nothing is written until all pass

The publish aborts before touching OneDrive. Each stop means something specific.

  1. Power BI Desktop is running Close it. Desktop holds file locks and rewrites .pbi/ caches mid-copy.
  2. The local repo has uncommitted changes Commit or stash. Without a commit there is nothing to roll back to.
  3. Tooling reached the deliverable Something matched claude or gemini in a published file — often a CLAUDE.md citation inside an M or DAX comment. Fix it at the source, not with the override flag.
  4. Structural check failed Missing .pbip, missing model.tmdl, or no report pages. The build is broken — do not publish around it.
  5. The deliverable collapsed File count dropped below 60% of the last publish. Usually a broken build. If the deletion is real, re-run with --min-ratio.
  6. The OneDrive side drifted Someone edited the deliverable directly. Go to section 04 — do not reach for --force-overwrite to make it quiet.
  7. Post-copy verification failed The target does not match staging. The snapshot has already been restored automatically; the message names it.
Rollback

Every publish snapshots the target to ~/.claude/pbi-sync/snapshots/<slug>-<timestamp>/ first, keeping the last three. The deliverable is also its own git repo — git log there shows one commit per publish.

04

Someone edited the deliverable

Rare, but it happens. The pull lands their work on a review branch in your repo instead of overwriting either side.

sh ~/.claude/pbi-sync/bin/pbi-pull.sh sales-report

# it creates onedrive-pull/<timestamp> and leaves you on it
git diff main..onedrive-pull/<timestamp>
git switch main && git merge onedrive-pull/<timestamp>

Then publish normally. Same preconditions: Desktop closed, local tree clean.

05

Setting up another machine

git clone https://github.com/<owner>/pbi-pack.git C:/dev/pbi-pack
cd /c/dev/pbi-pack
sh scripts/install-hooks.sh       # .git/hooks are never cloned
sh scripts/sync-skills.sh         # skills/ -> ~/.claude/skills/
sh scripts/install-pbi-sync.sh    # tooling + session hooks -> ~/.claude/

Then, per project:

git clone <remote> C:/dev/pbi/<slug>
sh ~/.claude/pbi-sync/bin/pbi-register.sh <slug> C:/dev/pbi/<slug> "<onedrive path>"
Do not copy the registry

projects.json embeds this machine's Windows profile name in every OneDrive path. Copied to a machine where the account is named differently, it points publishes at folders that do not exist. Re-register instead — three arguments per project.

~/.claude/pbi-sync/state/ is per-machine too. On a fresh machine every project reads as never-published until its first publish, and the drift gate will refuse --init against a folder that is already a deliverable repo. That is correct — reconcile with pbi-pull.sh.

If the network blocks outbound SSH

Outbound port 22 is blocked, so git@github.com: remotes hang for two minutes and fail while HTTPS ones work — which reads as a per-repo fault. Add this to ~/.ssh/config before cloning:

Host github.com
  Hostname ssh.github.com
  Port 443
  User git
06

Adding a new project

  1. Start Claude in C:\dev\pbi-pack and let power-bi-dev run step zero.
  2. Scaffold from pbi-starter/ into C:\dev\pbi\<slug> — never into OneDrive.
  3. Fill README.client.md. It publishes as README.md; the repo's own README.md is tooling and stays local.
  4. Confirm .gitattributes is present — Hard Rule 19, or every Desktop save becomes a full-file diff.
  5. Keep CHANGELOG.md free of tooling entries. It ships to the client.
  6. Register it, then pbi-publish.sh <slug> --init.
07

Troubleshooting

SymptomCauseFix
git push hangs ~2 min, then fails — but only on some repos Port 22 blocked; those repos use SSH remotes, the working ones use HTTPS Add the SSH-over-443 block to ~/.ssh/config
fatal: mmap failed: Invalid argument Git repo corruption — files inside .git/ that exist but cannot be read Run git fsck, delete the named unreadable files if they hold nothing unique, re-fetch tags
Mass of modified files, empty git diff CRLF flip from a Desktop save Check git ls-files --eol. If .gitattributes is missing, add it and renormalize as its own commit
Publish says a registered project is not in the registry Fixed — was a stray carriage return from Windows Python Re-run install-pbi-sync.sh to get the current scripts
Custom visual renders as an empty rectangle A changed GUID broke every field binding Never regenerate visual.guid. Re-import the correct build
Refresh fails naming an unrelated table One table's error cancels the whole load Look for duplicate keys on the one-side of a relationship, not at the table named
Lock held by a dead run A publish crashed mid-flight Reclaims itself after 2 h, or remove ~/.claude/pbi-sync/locks/<slug>.lock
08

Never do these

  • Never open Claude or Power BI Desktop on a OneDrive - <Org> path. Those folders are publish targets. Anything you do there shows up as drift and blocks the next publish.
  • Never git init or edit files in a deliverable folder. pbi-publish is its only writer.
  • Never edit the scripts in ~/.claude/pbi-sync/bin/. They are installed copies. Edit scripts/pbi-sync/ in the pack; the pre-commit hook reinstalls them.
  • Never use --force-overwrite to silence a drift warning. It discards someone's work. Pull first.
  • Never edit TMDL with sed or a heredoc. Indentation is tab-sensitive and silently becomes spaces.
  • Never commit a model change as validated without a Desktop refresh. Git accepts text in any state; only Desktop proves the model loads.
